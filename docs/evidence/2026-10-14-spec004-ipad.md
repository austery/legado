## Follow-up: local-network recovery and in-flight selection passed

Tested on 2026-10-15 around 07:27-07:40 America/Toronto through Device Hub
on the same physical iPad Air 5, iPadOS 27.0.1. All installation and interaction
steps targeted the isolated Search Acceptance app. The earlier blocked result
above remains a dated observation; it is superseded for this installation by
this recovery and acceptance run.

### Permission diagnosis and recovery

- Original isolated build 7 reproduced `Local network prohibited`, with no
  fixture requests. Its packaged local-network usage declaration was present.
- Temporary diagnostic build 8 read that declaration from the running app bundle
  and attempted a native TCP connection. It showed `Network is down`; recompiling
  and reinstalling alone had not resolved access or produced a prompt.
- Temporary build 9 added a Bonjour browser and the corresponding service
  declaration. After invoking it and opening Settings, the system displayed
  Search Acceptance's local-network prompt. Allow was selected; returning to the
  diagnostic app showed a successful TCP connection to the fixture.
- The original isolated build 7 IPA was then reinstalled. Device inventory
  confirmed version 0.1.0 (7), and the temporary diagnostic UI was absent before
  acceptance. Its unchanged search implementation now reached the fixture.

This establishes a successful permission recovery after the Bonjour diagnostic
flow, not why the OS failed to prompt for earlier direct-IP requests. No privacy
reset, public tunnel, global network-protection change, or product-code workaround
was used. Diagnostic builds and sources remain local and are not included in
this PR. Local device builds and IPA structure checks passed for diagnostics;
no native/hosted test suite was rerun for this documentation-only follow-up.

### Physical interaction and timing

The isolated app retained exactly two synthetic enabled sources. Searching
`Shared work` returned one fast candidate while the slow endpoint held its reply.
The UI showed `Searching · 1/2 sources`, and an actual disclosure tap exposed
`Acceptance fast` with its exact candidate URL. Early screenshot-heavy attempts
ran past the unchanged 15-second client timeout and were discarded as evidence
of in-flight selection. The final repeated sequence batched the already observed
Search, disclosure and candidate taps, then displayed `Exact fast` details and
`fast chapter` in the catalog. Opening that chapter displayed both
`fast paragraph one.` and `fast paragraph two.` on the physical iPad.

The local fixture event log corroborates the final run (Unix seconds; elapsed
values are relative to that run's slow-held event):

| Event | Timestamp | Elapsed |
| --- | --- | --- |
| Slow search received | 1792064365.712799 | approximately 0 s |
| Fast search received | 1792064365.712887 | approximately 0 s |
| Slow response held | 1792064365.713246 | 0 s |
| Fast candidate details requested | 1792064368.364722 | 2.651 s |
| Fast catalog requested | 1792064368.397984 | 2.685 s |
| Fast chapter body requested | 1792064377.487571 | 11.774 s |

No slow response was released or expired between these events. Candidate
selection therefore reached details before the slow response or its 15-second
client timeout, and chapter content was requested before that timeout as well.
Selecting a candidate cancels the search session by design: this accepts entry
from an unfinished search, not continued background searching after navigation.
The confirming body screenshot proves rendered content, rather than inferring
readability solely from an HTTP request. The slow fixture was released and the
server stopped after the test.

**Result: passed for this controlled physical sequence on restored build 7.**
This closes the previously pending in-flight expansion/selection check. It does
not certify arbitrary community sources, paging/retry/restart, or shelf resume.
